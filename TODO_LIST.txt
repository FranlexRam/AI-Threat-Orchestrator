Para que el sistema sepa quién es quién, mañana cuando adaptemos el entorno agregaremos una tabla de Usuarios conectada a tus clientes. La estructura lógica se vería así:

Rol SUPERADMIN (Tú / SAKTI Core): Tu usuario no está amarrado a ninguna empresa en particular (su campo empresa_id o empresa_name es NULL o GLOBAL). Tiene permiso de ver absolutamente todo.

Rol CLIENT_ADMIN (Tú cliente - Empresa Alfa C.A.): El usuario de tu cliente está estrictamente amarrado a su registro de empresa. Tiene prohibido ver registros cuyo origen sea distinto al suyo.

2. ¿Cómo se construye la lógica en el Dashboard (app_saas.py)?
En tu Dashboard de Streamlit, la magia ocurre en dos fases: el Login y la Consulta Dinámica.

Fase A: El Sistema de Autenticación (Login)
Cuando alguien entra al Dashboard (localhost:8501), lo primero que verá es una pantalla limpia de inicio de sesión que le pide su Usuario y Contraseña. Al presionar "Ingresar", Streamlit valida los datos en Postgres y guarda dos variables cruciales en la memoria de la sesión (st.session_state):

El Rol del usuario (SUPERADMIN o CLIENT_ADMIN).

El Nombre de la Empresa asociado a ese usuario.

Fase B: Consultas Inyectadas Dinámicamente (Filtro Tenant)
En lugar de traer todos los incidentes con un comando genérico, modificamos la función que alimenta las gráficas y la dona de Plotly para que use condicionales basados en quién inició sesión.

# Lógica conceptual de aislamiento en el Dashboard
user_rol = st.session_state["rol"]

if user_rol == "SUPERADMIN":
    # 🌍 VISTA GLOBAL: Tú ves los ataques de todo el ecosistema juntos

PUNTO 2: Condiciones del Mini-Web Vulnerable (vulnerable-client-demo)

💣 Las 7 Vulnerabilidades que debemos sembrar (para poder atacarlas)
Para demostrar los 7 vectores que tienes mapeados en tu Dashboard, configuraremos el sitio web con los siguientes "errores de programación" controlados:

1. Brute Force Attack
La condición en el sitio: El formulario de login no debe tener políticas de bloqueo de cuenta ni rate-limiting nativo. Debe permitir que cualquiera intente loguearse infinitas veces.

La demostración: Al mandar la ráfaga con el simulador, el sitio web dejará pasar los primeros dos intentos, pero al tercero, tu motor de correlación temporal lo detectará en la RAM, activará el bloqueo perimetral y el sitio web pintará el "Acceso Denegado".

2. SQL Injection (SQLi)
La condición en el sitio: Crearemos un buscador de productos donde la consulta SQL se construya concatenando texto directamente, sin usar parámetros seguros:
query = f"SELECT * FROM productos WHERE id = '{id_solicitado}'"

La demostración: Al atacar con un payload como ' OR 1=1 --, tu API detendrá la petición en el aire antes de que llegue a tocar esa consulta rota, salvando la base de datos de ser expuesta.

3. Cross-Site Scripting (XSS)
La condición en el sitio: Un cuadro de comentarios o un buscador que refleje en la pantalla exactamente lo que el usuario escribió, sin limpiar las etiquetas HTML.

La demostración: Intentaremos inyectar <script>alert('Hacked')</script>. Tu software interceptará los caracteres especiales y congelará la carga de la página.

4. Directory Traversal
La condición en el sitio: Un endpoint que sirva archivos del sistema usando un parámetro de ruta directo, por ejemplo: /ver-archivo?file=imagen.jpg, procesado internamente con un lector de archivos plano.

La demostración: Al simular el ataque intentando leer carpetas raíz (/ver-archivo?file=../../../../etc/passwd), los disparadores web del pipeline bloquearán la solicitud.

5. Remote Code Execution (RCE)
La condición en el sitio: Una función expuesta en el servidor que interactúe directamente con la consola de comandos del sistema operativo subyacente (por ejemplo, un botón para hacer un "ping" a una IP que use un os.system() directo).

La demostración: Al meter comandos encadenados como ; whoami o ; netcat, saltará la alerta crítica perimetral.

6. Server-Side Request Forgery (SSRF)
La condición en el sitio: Una función que permita al sitio web "importar una foto de perfil desde una URL externa" usando una librería de peticiones en el backend (como requests.get(url_usuario)).

La demostración: Atacaremos el sitio pidiéndole que consulte las IPs de metadatos internos de AWS/Cloud (169.254.169.254), y el orquestador cortará el flujo de inmediato.

7. Distributed Denial of Service (DDoS)
La condición en el sitio: El servidor web debe estar configurado de forma sencilla (un solo hilo o proceso Worker) para que sea vulnerable a la saturación por peticiones concurrentes masivas.

La demostración: Aquí es donde brillará el nuevo cambio que planeamos para la próxima sesión. Lanzaremos cientos de peticiones simultáneas desde el simulador. Tu motor perimetral identificará el pico anómalo de tráfico por segundo global y empezará a descartar las conexiones maliciosas en el perímetro para mantener el sitio web real completamente en línea y ligero para los usuarios legítimos.
